Partner API for robot cleaning data

A read-only HTTP API for retrieving cleaning task reports from the robots you service. Exchange your credentials for an access token, list your robots, then pull their task history by date.

Version v1 Updated September 2026 Format JSON over HTTPS Access Read-only Audience PCS engineering

Before you start

RAASPAL issues you two values: a client id and a client secret. You exchange them for a short-lived access token, then send that token on every data request. This is the standard OAuth 2.0 client credentials grant, so most HTTP and OAuth libraries support it directly.

ItemValue
Base URL https://api.raaspal.com
Token endpoint POST /api/partner/v1/oauth/token
Auth header Authorization: Bearer <access_token>
Token lifetime 24 hours
Rate limit 120 requests per minute for data endpoints, plus 20 per minute for the token endpoint

The client id is not sensitive — RAASPAL can tell you again at any time. The client secret is shown only once when it is created and cannot be recovered; store it in your server's environment configuration. If it is ever exposed, ask RAASPAL to revoke it and issue a new one — revocation takes effect immediately, including for tokens already issued.

Getting a token

Send the three fields below to /oauth/token. The endpoint accepts them in three interchangeable formats — pick whichever your client makes easiest. All three return exactly the same response.

Option 1 — JSON body

The easiest option in Postman, and the one most HTTP libraries produce by default.

POST /api/partner/v1/oauth/token
Content-Type: application/json

{
  "grant_type": "client_credentials",
  "client_id": "cid_your_client_id",
  "client_secret": "pk_your_client_secret"
}
curl -X POST "https://api.raaspal.com/api/partner/v1/oauth/token" \
  -H "Content-Type: application/json" \
  -d '{
    "grant_type": "client_credentials",
    "client_id": "cid_your_client_id",
    "client_secret": "pk_your_client_secret"
  }'

Option 2 — form-encoded body

What the OAuth 2.0 specification defines, so off-the-shelf OAuth libraries use this.

POST /api/partner/v1/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=cid_your_client_id&client_secret=pk_your_client_secret
curl -X POST "https://api.raaspal.com/api/partner/v1/oauth/token" \
  -d "grant_type=client_credentials" \
  -d "client_id=cid_your_client_id" \
  -d "client_secret=pk_your_client_secret"

Option 3 — HTTP Basic

Credentials in the header instead of the body, also permitted by the specification.

POST /api/partner/v1/oauth/token
Authorization: Basic base64(client_id:client_secret)
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials

The response — identical for all three

{
  "access_token": "eyJhbGciOiJIUzI1NiJ9...",
  "token_type": "Bearer",
  "expires_in": 86400
}

Using Postman

In the request's Body tab choose raw, then set the dropdown beside it to JSON — not Text. That dropdown is what sets Content-Type, so do not add a Content-Type header yourself on the Headers tab.

Getting this wrong is the most common cause of a failed first request. Two symptoms and what they mean:

  • "error": "invalid_request" — the body could not be read at all, usually because the dropdown is on Text, or a Content-Type header was set by hand that does not match the body. The message echoes the Content-Type we received, which tells you which it was. Your credentials are not the problem.
  • "error": "invalid_client" — the body was read correctly, but the client_id or client_secret is wrong, revoked or expired. Check them, or ask RAASPAL to confirm the client id.

Using the token

curl -H "Authorization: Bearer eyJhbGciOiJIUzI1NiJ9..." \
  "https://api.raaspal.com/api/partner/v1/robots"

Caching and refreshing

Do not request a new token for every call. Cache it and reuse it until it expires — roughly one exchange per day. When a data request returns 401, fetch a fresh token and retry that request once. That refresh-and-retry loop is the only token handling your integration needs. Read expires_in from the response rather than hard-coding 24 hours, so a future change to the lifetime does not break your client.

Checking your credentials

GET /api/partner/v1/me confirms a token is valid and names the account it belongs to. You do not need it to integrate — it is there to test a new credential, or to work out whether a problem is your authentication or your data. 

{
  "success": true,
  "data": {
    "partnerId": "8f21c0d4-3b7a-4e19-9f42-6c8a1d5e77b3",
    "partnerName": "PCS",
    "apiKeyId": "1c9e5a72-40bd-4f86-b0d1-2e4437a9c810"
  },
  "timestamp": "2026-07-27T05:07:49.615530267"
}

A 200 means your credentials work. If this succeeds but List your robots comes back empty, authentication is fine and no robots have been assigned to your account yet — contact RAASPAL rather than assuming an integration fault.

How current is the data

These endpoints return data RAASPAL has already collected from the robot manufacturer and stored — they do not query the robot live. Task reports appear after RAASPAL's scheduled sync has run, so a task finished minutes ago may not be available yet. Historical data does not change once synced.

Endpoints

Two endpoints, in the order you will use them.

  • 01 — List your robots
  • 02 — Fetch task reports
01 GET /api/partner/v1/robots

Every robot assigned to you, with the customer and site it is installed at. The serialNumber is the identifier you pass to the task-reports endpoint — this is how you discover which robots you can query. 

{
  "success": true,
  "data": [
    {
      "serialNumber": "GS401-6220-W9R-K100",
      "brand": "GAUSIUM",
      "model": "Omnie",
      "name": "Makro ST075 Thalang - Omnie",
      "site": "makro ถลาง ภูเก็ต (Thalang, Phuket)",
      "customerName": "PCS : Makro"
    }
  ],
  "timestamp": "2026-07-27T05:07:49.615530267"
}

If a robot you expect is missing, it has not been assigned to your account yet — contact RAASPAL rather than querying it directly, as it will return 404.

02 GET /api/partner/v1/robots/{serialNumber}/task-reports

The cleaning task history for one of your robots, newest first. Results are paginated.

Query parameters

ParameterFormatDescription
startTimeMinYYYY-MM-DD Earliest task start date, inclusive. Sent on its own, returns that single day.
startTimeMaxYYYY-MM-DD Latest task start date, inclusive.
monthYYYY-MM A whole calendar month. Ignored if startTimeMin or startTimeMax is present.
pageinteger Page number, starting at 0. Default 0.
sizeinteger Results per page. Default 20, maximum 100.

Dates are dates only — 2026-07-01, not 2026-07-01 00:00:00. Sending a time returns 400 rather than silently narrowing your range.

The date you send is a Thailand calendar day (Asia/Bangkok), while the timestamps in the response are UTC. So a task that ran at 04:00 on 25 July in Bangkok is matched by startTimeMin=2026-07-25, and comes back with a start time of 2026-07-24T21:00:17Z. Both describe the same moment. 

GET /api/partner/v1/robots/GS401-6220-69R-0100/task-reports
      ?startTimeMin=2026-07-25&startTimeMax=2026-07-25&page=0&size=20

Response

data holds one page of results. totalElements is the number of matching tasks overall, and totalPages tells you how many requests it takes to read them all.

Field reference

externalTaskId
Unique id for the task, stable across requests — safe to use for deduplication.
cleaningPlan
Name of the cleaning plan the operator ran, as configured on the robot.
robotSerialNumber / brand
Echoed back so a page of results is self-describing.
mapName
The floor map the task ran on, as named on the robot. null for the occasional task where the manufacturer reports no map.
cleaningMode
The cleaning mode in English. The robots report this in Chinese, and inconsistently across firmware versions, so RAASPAL normalises it to one of a fixed set. The English wording is Gausium's own, confirmed by them against every value present in the fleet:
  • Scrubbing · Washing · Scrub & Sweep
  • Dust Mopping · Mopping · Wet Mopping
  • Sweeping · Sweep & Vacuum · Vacuuming · Water Sucking
  • Light Cleaning · Medium-Duty Cleaning · Heavy-Duty Cleaning
  • Patrol Inspection — an inspection run, not a cleaning task
Safe to group and count on: one activity always yields one label, even where different robots report it differently. An unrecognised mode reads as Other. The manufacturer's untranslated value is not included in the response.
taskCompletionPct
Percentage of the planned area actually covered.
startTime / endTime
ISO-8601 timestamps in UTC (the trailing Z). Gausium's own report pages show the same instants in the robot's local time, so a task shown there as 04:00 in Bangkok appears here as 21:00Z the previous day — add 7 hours to convert.
workingTimeSeconds
Time the robot was actively working, excluding pauses, docking and obstacle waits. This is normally less than endTime − startTime — use the timestamps for elapsed time and this field for productive time.
plannedAreaSqm / cleaningAreaSqm
Planned versus actual area cleaned, in square metres.
workEfficiencySqmH
Square metres cleaned per hour.
waterConsumptionL
Water used, in litres. Zero for dry cleaning modes.
startBatteryPct / endBatteryPct
Battery level at the start and end of the task.
brushResidualPct
filterResidualPct
suctionBladeResidualPct
Remaining life of each consumable — useful for planning maintenance visits.
taskEndStatus
How the task ended, as reported by the robot:
  • 0 Completed — the task ran to the end.
  • 1 Manually terminated — an operator stopped it. Can happen at any point, including near completion, so a high taskCompletionPct with this status is normal.
  • 2 Abnormal termination — the robot stopped early, e.g. a fault or a blocked route.
  • 3 Startup failure — the task never began.
  • null Treated as completed — a finished task that reported no explicit status.
RAASPAL applies this same mapping in the monthly performance reports sent to customers, so the two always agree.
operator
Account that started the task.
reportMonth
Calendar month the task is grouped under, as YYYY-MM.

Responses and errors

Every response has the same envelope: a success flag, a data payload on success or a message on failure, and a timestamp.

StatusMeaningWhat to do
200 Success. Read data.
400 A parameter is malformed — usually a date with a time in it, or a month that is not YYYY-MM. Read message; it names the parameter and the expected format.
401 The token is missing, malformed, or expired — or the credential behind it was revoked. Fetch a new token and retry once. If that also fails, contact RAASPAL — the credential may have been revoked or expired.
401 {"error": "invalid_client"} from the token endpoint: the client id or secret is wrong, or the credential is revoked, expired, or disabled. Check both values. The error is deliberately identical for every cause, so contact RAASPAL if they look correct.
404 That serial number is not one of your robots, or does not exist. Confirm the serial against /robots.
429 You exceeded 120 data requests in a minute — or 20 token requests, which usually means the token is being fetched per call instead of reused. Wait the number of seconds in the Retry-After header, then retry. 
{
  "success": false,
  "message": "No robot with serial number 'GS401-0000-0000' is available to this partner",
  "timestamp": "2026-07-27T05:07:49.615530267"
}

Staying within the rate limit

Successful responses include X-RateLimit-Limit and X-RateLimit-Remaining so you can pace a large job rather than discovering the limit by hitting it. Pulling a month of history for a large fleet is well within budget if you request one robot at a time.

The token endpoint has its own smaller budget of 20 requests per minute, counted per IP address rather than per client id, because a caller has no identity until the exchange succeeds. Reusing a token for its full 24 hours needs one request a day, so this only bites a client that exchanges credentials before every call — the usual cause of an unexpected 429 on /oauth/token. Cache the access_token until it expires.

A worked example

Pulling last month's cleaning data for your whole fleet:

  1. Exchange your credentials once at /oauth/token and keep the token. Reuse it for the whole job — it lasts 24 hours, far longer than the run will take.
  2. Call /robots once and keep the list of serial numbers.
  3. For each serial, call /task-reports?month=2026-06&size=100.
  4. If totalPages is greater than 1, request the remaining pages with page=1, page=2, and so on.
  5. Store rows against externalTaskId. It never changes, so re-running the job will not create duplicates.

Questions about access, a key that stopped working, or a robot missing from your list — contact your RAASPAL representative. This document describes v1 of the Partner API; any breaking change will be announced before it takes effect.
